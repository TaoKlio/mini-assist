# mini辅助 (mini-assist)

Mindustry **v160** 辅助 mod。由两个独立 mod 合并而成——「钻机产出分析器」(drill-output) 与
「内存块读写助手」(memory-access)——现在共用一个 jar、一个设置分类。

| 功能 | 做什么 | 联机 |
|---|---|---|
| **钻机产出** | 按住 **F** 框选，选区左上角按矿物逐行显示框内钻机的**净输出**与**实际输出** | 可用（纯客户端只读，服务器无需安装） |
| **内存块读写** | 悬停内存块时出现读/写图标：读=整块复制到剪贴板，写=从剪贴板写回数字槽 | 仅单机（`net.active()` 时自动停用） |

两个功能彼此独立、互不引用；mod 带 `hidden` 标签，装了它仍可进入任意服务器。

---

## 一、钻机产出

面板每行 = 矿物图标 + `净 X/s   实际 Y/s`，两个数值都保留 **2 位小数**：

| 显示项 | 含义 |
|---|---|
| 净 X/s | **净输出 = 额定理论产出**（满水、满效、满预热、不计超速）：只由「钻机配置 + 覆盖矿格数 + 接水标志」决定，**是一组定值**，不会被满仓 / 缺电 / 水压抖动搅动 |
| 实际 Y/s | 真实产出速率；口径由「取平均值」决定：**开 = 时间平均（含停机时间）** / 关 = 瞬时速率（与游戏速度条同口径） |

- 选区**只要覆盖 1 格就统计**：框住一台只占 1 格的钻机也能出数据（只有整块选区落在地图外时才不统计）。
- 行按**矿物**聚合，**每台钻机都参与建行**：被开关排除的钻机在该行按 0 累加，行集合保持稳定、不会闪烁。
- 选区边长上限**默认 200 格、可在设置里调**，超出会截断并在鼠标旁标注原始尺寸。
- 松开按键后结果保留在屏幕上。

### 操作

1. 按住 **F**（可在设置里改为任意按键名，如 `g`、`r`、`mouseMiddle`）；
2. 移动鼠标——矩形框以按下点为锚点，向鼠标方向生长；
3. 松开按键，结果保留在屏幕上供查看。

### 净输出的两个开关

设置页「钻机产出 → 净输出」有一行说明，其下两个开关：

| 设置项 | 默认 | 说明 |
|---|---|---|
| 计入电力未连接的钻机 | 开 | 关闭后，未接电（电力效率为 0）的钻机不再把额定产出计入净输出 |
| 计入容量已满的钻机 | 开 | 关闭后，产物已满仓的钻机不再把额定产出计入净输出 |

停机原因按 **被禁用 → 无矿 → 满仓 → 无电** 取**首个命中**，所以同时满仓又缺电的钻机归类为「满仓」，
只受第二项影响。两个开关只作用于**净输出**：被排除的钻机仍照常统计实际输出。

> 「净输出」的口径恒定为**额定可达值**（按实际覆盖矿格数与接水状态）。游戏悬停面板里那个
> `60 / drillTime × size²` 是另一个口径（假设满格矿、不接水、不看硬度），本 mod 不再提供切换——
> 两者的区别见「对照：游戏自己怎么对待速度」一节。

### 选区显示：边框与范围文字是两个独立开关

| 设置项 | 默认 | 作用 |
|---|---|---|
| **选区范围文字** | **开** | 在选区**内部第一行**显示尺寸（如「选区 8x6 格」，含「已从 WxH 截断」提示） |
| **选区边框** | **关** | 是否绘制矩形边框（纯装饰，关掉界面更干净） |

```
┌──────────────────────────────┐   ← 边框（默认不画）
│ 选区 8x6 格                   │   ← 范围文字：框内第一行
│ ● 净 1.20/s   实际 1.50/s     │   ← 每行一种矿物
└──────────────────────────────┘
```

- 范围文字**不再跟鼠标飘**，而是固定在选区内部第一行，随面板一起收进边框内；
- 面板整体会按选区尺寸自动收紧字号，**不会越出选区**（屏幕字号下限为镜头补偿字号的 70%，
  再小就不缩了——见下节「字号规则」，避免位图字体被缩糊）；
- 锚点每帧按当前选区重算，拖动时面板跟手不滞后。

### 净输出是一组定值（历经三次返工才定下来）

**症状**：时断时动的钻机（水压不足反复断供、一会儿满仓一会儿空出位置）会让净输出上下跳，
而「理论值」本应是定值。

**两次失败的方向**（留个记录，免得以后又走回去）：

| 尝试 | 做法 | 为什么失败 |
|---|---|---|
| ① 对瞬时判定加滞回 | 仍按公式现算，但「接水 / 停机」用连续 N 次才改判 | 只压制抖动；慢周期（>1 秒）的水循环照样让它跳，且滞回窗口越长越迟钝 |
| ② 改观测峰值 | 取 `60 × lastDrillSpeed` 的历史峰值，不再现算 | **测量必然带噪声**：峰值会随当前值的微小波动缓慢爬升 / 衰减，数字仍在游走 |

**现在的做法：公式化 + 只保留慢变量。**

```java
净输出/台 = 60 × (接水 ? liquidBoostIntensity² : 1) × dominantItems / getDrillTime(item)
```

这个式子里**没有任何每帧都在变的量**：

- 钻机配置（`drillTime`、`liquidBoostIntensity`）静态；
- `dominantItems` 只在**邻近方块变化**时由游戏重算（`onProximityUpdate`），不是每帧；
- `efficiency`（电力）、`warmup`（预热）、`lastDrillSpeed` **全都不参与**——满效、满预热按额定算；
- 唯一的跨帧输入是**接水标志**：观测到接水即置真，连续断水 `DRY_LATCH_SCANS = 50` 次（约 5 秒）
  才降为无加成，**且停机期间不累计断水**。水压抖动、临时断供都改不了它。
- **「接了水」看液罐，不看 `optionalEfficiency`**：后者是「本帧实际消耗量」换算出来的，而满仓 /
  被禁用时 `shouldConsume()` 为假、钻机根本不吸水，它自然也是 0——那并不代表没接水。
  所以判定以 `build.liquids.currentAmount() > 0`（液罐里有水）为主、`optionalEfficiency` 为辅。
  这个 bug 的实际表现：**4 台钻机全速加水时净输出 19.95/s，其中 2 台满仓后掉到 12.52/s**——
  满仓的钻机被误判成「断水」，额定值从 `boost²` 掉到 1 倍；反推能解出 `boost² ≈ 3.9`，
  与现场的钻机加成吻合。现在满仓不影响接水状态，读数不再变。

于是只要**钻机与地形不变，读数就是定值**；停机（满仓 / 缺电 / 被禁用）只通过两个设置开关决定
「算不算这台」，**不影响数值本身**。会抖、会归零的那个量留给**「实际」**那一列（它本来就要反映真实产出）。

另外面板**行序按「净输出」排序**（原来按「实际输出」——那是个会跳的量，两行会反复交换位置）。
净输出是定值，同值时用矿物 id 兜底，行序因此确定不动。

### 「已从 WxH 截断」是什么意思

统计选区有**每边上限**（设置项「选区边长上限」，默认 **200 格**）。框选超过这个尺寸时，只会**从选区
坐标较小的一角保留上限内的格数**参与统计，超出部分完全不统计，于是鼠标旁补一句「（已从 WxH 截断）」
把**原始选区尺寸**告诉你——看到这句，就说明左上角面板的数字只覆盖了框内的一部分。

为什么要有上限：一次框住半张地图时，每 6 帧要遍历上万个格子。上限 S 意味着单次遍历最多 S² 格
（200 → 4 万格，800 → 64 万格），所以**调大后在大地图上可能掉帧**。若选区越过地图边界，会先被裁到
地图内再计算尺寸，这种情况**不算**截断（不显示该提示）。

### 字号规则（自动，无开关）

面板绘制在**世界坐标**里，字号必须同时满足两个要求，二者合成**一套自动规则**、不提供单独开关
（分开开关会让两个机制互相打架，产出既不贴合选区、又糊的字号）：

1. **镜头补偿**：`基准镜头 / 当前镜头`，让屏幕上的像素尺寸恒定——
   基准取游戏默认镜头 `Scl.scl(4f)`（`Renderer.targetscale` 的初值），取
   `renderer.getDisplayScale()`（当前实际缩放）而非 `getScale()`（目标值），缩放动画中不抖；
2. **收进选区**：再用 `GlyphLayout` 实测面板文本尺寸，按选区大小收紧，保证不越出选区。

**下限 0.7**：最终屏幕字号最小只缩到镜头补偿字号的 70%。位图字体缩太多会糊，
而「镜头拉得很远 + 选区很小」正是两个机制相乘后最容易踩线的组合；此时宁可让面板在极小选区里
略微溢出，也不把字缩到看不清。

> 该系数同时驱动行距、图标尺寸与行内偏移，因此缩放后布局比例不变、不会互相重叠。

### 计算口径

净输出是**额定理论值**：`60 × boost² × dominantItems / getDrillTime(item)`（满水、满效、满预热、不计超速）。
式中每个量都来自游戏侧原式，见 `Drill.DrillBuild.updateTile()`：

```
delay          = getDrillTime(dominantItem)
               = (drillTime + hardnessDrillMultiplier × item.hardness) / drillMultipliers[item]

speed          = lerp(1, liquidBoostIntensity, optionalEfficiency) × efficiency

lastDrillSpeed = speed × dominantItems × warmup / delay        // 个/帧
warmup         = approachDelta(warmup, speed, warmupSpeed)      // ← 预热收敛到 speed，不是 1
progress      += delta() × dominantItems × speed × warmup       // ← 产出 ∝ speed × warmup

稳态（warmup → speed）：
额定产出/秒    = 60 × speed² × dominantItems / delay             // 满水满效率即 boost² ← 这就是「净输出」
实际/秒        = 60 × lastDrillSpeed × timeScale()               // 实时值，会抖
```

**加水加成是平方的（`boost²`）**：产出速率是 `speed × warmup`，而预热值收敛到 `speed` 本身
（`approachDelta(warmup, speed, …)`，不是收敛到 1），所以稳态倍率必然是 `speed²`。
满水满效率时 `speed = liquidBoostIntensity`，实际产出就是 `liquidBoostIntensity²` 倍——
默认 1.6 → 2.56×，爆破钻 1.8 → 3.24×，与游戏信息面板 `Drill.setStats()` 写的
`liquidBoostIntensity * liquidBoostIntensity` 完全一致。

**`timeScale`（超速）只补在「实际」上，不补在「净」上**：`lastDrillSpeed` 是按帧量、不含超速倍率，
游戏自身的速度条就是这么换算的——见 `Drill.setBars()`：`Strings.fixed(e.lastDrillSpeed * 60 * e.timeScale(), 2)`。
超速经 `Building.applyBoost()` 只写 `timeScale`、**不写 `efficiency`**，所以不存在重复计数。

### 对照：游戏自己怎么对待「速度」

看传送带能印证一件事——**游戏对「速度」分两套：额定（声明）与实时**。

| 方块 | 额定/声明值 | 实时值 |
|---|---|---|
| 传送带 | `Conveyor.displayedSpeed`（**手工声明**的 items/秒，例：`Stat.itemsMoved`） | **没有**（`Conveyor` 未覆写 `setBars()`，无实时速度条） |
| 钻机 | `Stat.drillSpeed = 60/drillTime × size²`（信息面板，假设满格矿） | `bar.drillspeed`＝`lastDrillSpeed × 60 × timeScale()`（状态条） |

`Conveyor.setStats()` 里作者自己写了注释：

```java
//have to add a custom calculated speed, since the actual movement speed is apparently not linear
stats.add(Stat.itemsMoved, displayedSpeed, StatUnit.itemsSecond);
```

也就是说：**传送带那个「速度」不是测出来的，是作者手填的定值**——因为真实移动与吞吐不是线性关系。
钻机同理，`Stat.drillSpeed` 也是静态额定值（且假设 `size²` 格全是矿、不接水）。

> 结论：想「像传送带那样拿到一个恒定速度」，对应的就是**额定值**——本 mod 的**「净」**：
> 用游戏公式 `60 × boost² × dominantItems / getDrillTime(item)` 算，比信息面板那个
> 「满格矿、不接水」的数更贴近真实（按实际矿格数、并按接水状态给加成）。
> 而**「实际」**只能是实时量：游戏对外只给了 `lastDrillSpeed` 一个来源。

### 游戏自带的判据：钻机状态条

`Drill.setBars()` 会给每台钻机加一条状态条，键名 `bar.drillspeed`（中文显示为「**挖掘速度：X/秒**」），
值就是——

```java
Core.bundle.format("bar.drillspeed", Strings.fixed(e.lastDrillSpeed * 60 * e.timeScale(), 2))
```

**选中/悬停钻机时就能看到它**。本 mod 的「实际」在「取平均值」**关**（瞬时口径）时与这条**逐字相同**
（同样保留 2 位小数）——所以对照基准就在游戏里，不必自己推算。

两个**看着像但口径不同**的数字，别混进来比：

| 数字 | 来源 | 口径 |
|---|---|---|
| 「挖掘速度：X/秒」状态条 | `lastDrillSpeed × 60 × timeScale()` | **实时**产出速率（mod 瞬时口径与之一致） |
| 建造预览 / 信息面板的 `60/drillTime × size²`（例如 11.1/s） | `Drill.drawPlaceText` / `Stat.drillSpeed` | **额定值**：假设 `size²` 格**全是矿**、且**不接水** |
| 本 mod 的「净」 | `60 × boost² × dominantItems / getDrillTime` | 按**实际覆盖矿格数**、计入接水，所以通常**低于**上面那个额定值 |

> `BeamDrill` 的状态条是 `lastDrillSpeed * 60`（**不乘** `timeScale`）——游戏自己在这点上不一致；
> 本 mod 统一乘 `timeScale`（与 `Drill` 系一致）。

### 「实际」列：平均产能（默认）与瞬时速率

**指标口径已定：平均产能**——`Σ真实产出 / Σ时间`，**停机时间也摊进去**。判据是**下游消耗**：
稳态下「生产 ≡ 消耗」，所以平均值应向长周期参照收敛。

**产出量怎么数**：不靠模型，直接数游戏的进度字段 `DrillBuild.progress`（public 字段）。
游戏每帧执行 `progress += delta() × dominantItems × speed × warmup`，达到 `delay` 就产出并
`progress %= delay`，所以本帧产出件数就是 `Δprogress / delay`（回绕时补回一个 `delay`）：

```java
float d = b.progress - st.prevProgress;
if(d < 0f) d += delay;                                // 刚产出过 → progress %= delay
float produced = Mathf.clamp(d, 0f, delay) / delay;   // 本帧产出件数（可为小数）

st.sliceAmount += produced;                           // 累进当前小片（0.05 秒一片）
st.sliceTime   += Time.delta;
if(st.sliceTime >= 3f){                               // 满 3 帧（0.05 秒）→ 封片进环形窗口
    st.sliceAmounts[st.sliceIndex]   = st.sliceAmount;
    st.sliceDurations[st.sliceIndex] = st.sliceTime;
    st.sliceIndex = (st.sliceIndex + 1) % 6;          // 窗口共 6 片 = 0.3 秒
    st.sliceAmount = 0f; st.sliceTime = 0f;
}
```

窗口内的值 = **窗口内产出量 ÷ 窗口实际时长**（60fps 稳定时就是「速度和 ÷ 0.3 秒」）：

```java
实际/秒 = 60 × Σ(6 片产出) / Σ(6 片时长)     // 含正在进行中的那一片，所以滑窗连续
```

于是**四种停机情形自动归零**，不需要额外的停机判定：

| 情形 | 为什么自动归零 |
|---|---|
| 被逻辑禁用 | `Building.update()` 跳过 `updateTile()` → `progress` 不动 |
| 无矿 | `Drill.updateTile()` 提前 `return` → 不动 |
| 满仓 / 缺电 | 走 `updateTile()` 的 else 分支 → 不累加 `progress` |
| 超速 / 预热 / 供水 | 已经包含在 `progress` 的增量里 |

**唯一边界**：一帧内产出 ≥2 件（约 ≥60 件/秒）时回绕无法精确还原 →
这类钻机（`60 × lastDrillSpeed × timeScale ≥ 55`）回退用 `lastDrillSpeed` 的积分。
两种口径在正常情况下代数等价，所以切换点不会跳。

| 设置「取平均值」 | 公式 | 回答的问题 | 停机时 |
|---|---|---|---|
| **开**（默认） | `60 × Σ产出 / Σ时间`（逐帧累加，**停机时间也摊进去**） | **平均产能**（对应下游消耗） | 拉低平均值 |
| **关** | `60 × lastDrillSpeed × timeScale`（游戏速度条同口径） | 它**现在跑多快** | 该帧为 0，但不摊进平均 |

「平均窗口（次统计）」默认 **30（≈3 秒）**：窗口太短（如旧默认 0.7 秒）会与长周期的「下游消耗」对不上。
钻机增减时块平均会立即重置并按新值显示，所以增减钻机是即时可见的。

**验证方法**（判据 = 下游消耗）：

1. 单机、无超速：一台钻机 → 传送带 → 一个**不会满**的容器（或直接送入消耗方）；
2. 等 ≥30 秒进入稳态；
3. 量下游消耗：容器库存增量 ÷ 时间；
4. 「平均窗口」设为 30–100（3–10 秒），与 mod 读数对照，**允差 ≤2%**；
5. 边界：堵住下游（满仓）→ 读数应变 0；断水 / 接水 → 平均值平滑过渡、无无理由的拐点。

> **联机**：不要求准确。本算法依赖 `progress`，它在联机下是否同步未经实测；
> `lastDrillSpeed` / `efficiency` / `warmup` 这类 Continuous 量按间隔同步，客户端天然滞后。
> 因此联机读数仅作参考。

### 「取平均值」的算法：两层平均

「取平均值」不是一层，而是**两层平均叠在一起**，各管一件事：

| 层 | 窗口 | 公式 | 作用 | 由谁决定 |
|---|---|---|---|---|
| **① 0.3 秒滑窗** | **0.3 秒**（每 **0.05 秒**断一小片，共 6 片） | `60 × Σ(窗口内产出) / Σ(窗口内时长)`（≈ 速度和 ÷ 0.3） | 让「实际」**准确**：含停机时间、帧率无关、无采样混叠 | 固定，无设置 |
| **② 块平均** | `N × 0.1 秒`（默认 N=30 → **3 秒**） | `(1/N) × Σ(① 的结果)` | 只做**显示稳定**：块内数字冻结，块边界才更新一次 | 「取平均值」+「平均窗口」 |

**① 的代码**（每帧，见 `Drills.accumulate()` / `windowRate()`）：每帧把真实产出累进 **0.05 秒的小片**，
满 3 帧就封片写入**环形窗口**（6 片 = 0.3 秒）；取值时把窗口内 6 片（含正在进行中的那一片）相加，
**除以窗口实际时长**。所以每个值都是**最近 0.3 秒**的真实时间平均，而且是**连续滑动**的、
不会每 0.05 秒跳一格。

**② 的代码**（每次统计刷新，见 `Row.push()`）：

```java
if(count != lastCount){            // 该矿物的钻机台数变了 → 丢弃半截的块
    size = 0; sumActual = 0f; lastCount = count;
    disActual = a;                 // 立即改用瞬时值显示
    return;
}
sumActual += a; size++;
if(size >= cap){                   // 攒满 N 次 → 更新显示并开新块
    disActual = sumActual / size;
    size = 0; sumActual = 0f;
}
```

要点：

- **② 是「平均值的平均」**：当每个 0.1 秒窗口长度相同时，它等价于「整块时间内的总产出 ÷ 总时间」；
- **块内冻结**：显示值在一个块内完全不动（默认每 3 秒跳一次），不会逐帧抖；
- **台数一变立即重置**：增减钻机时丢弃半截的块、改按瞬时值显示，所以增减是即时可见的；
  这也意味着**刚框选 / 刚增减时先看到的是瞬时值**，攒满一整块后才转为平均值；
- **关掉「取平均值」＝两层同时关闭**：`N` 取 1（每次统计都刷新），且「实际」本身改为**瞬时速率**
  （`60 × lastDrillSpeed × timeScale`，与游戏「挖掘速度」状态条逐字一致）；
- **「净」也走同一层 ②**：但它是定值，平均等于原值，只有「台数变化立即重置」对它有意义。

> 取舍：窗口越长越稳、越迟钝。默认 3 秒是为了对齐「下游消耗」这种长周期参照；
> 想跟手就调小（最小 1 = 0.1 秒），想极稳就调大（最大 1000 = 100 秒）。

### 多人游戏

钻机产出是**纯客户端只读**实现：只读取 `DrillBuild` 上由服务端同步的公开字段（`lastDrillSpeed`、
`efficiency`、`optionalEfficiency`、`dominantItem`、`dominantItems`、`timeScale()`），**不修改任何游戏状态、
不发送任何数据包**。因此服务器无需安装本 mod，其他玩家看不到你的选区框；真·联机时客户端读到的是
同步快照，数值可能比房主端滞后若干帧。

## 二、内存块读写

悬停内存块时，方块上方出现两个可点击图标：

| 图标 | 动作 |
|---|---|
| 读（📋） | 把内存块全部槽位编码后写入剪贴板（超过「最大复制长度」则提示失败，默认上限 16384） |
| 写（📄） | 解析剪贴板文本并写回**数字槽**；对象槽、坏行、越界地址会被跳过并计数 |

- **虚拟选中**：鼠标从方块移到图标上不会丢失选中，移出「方块 + 图标」区域才取消。
- **快捷键兜底**：选中状态下 `Ctrl+C` 读、`Ctrl+V` 写。
- **仅单机**：`net.active()`、非游玩状态、逻辑编辑器打开时功能自动停用。

### 实现说明

内存块在 v160 中是多槽结构（默认 32 槽，可被地图 / 内容改为 512、16384 等）。读写通过反射访问
`MemoryBlock.MemoryBuild` 的**私有**字段 `objectMemory` / `numberMemory`，并用静态哨兵 `sentinel`
区分数字槽与对象槽（见 `MemoryIO.java`）。这类反射是版本脆弱的：换游戏版本若改了字段名，
`MemoryIO` 的静态初始化会直接抛异常——`tools\VerifyApi.java` 里的 `declaredField` 校验就是为了
在构建期把这种问题提前抓出来。

> 保持浅色小字、不画线，避免与一等分节抢视觉。
>
> 开关行样式：灰底其实有**两层**，只清一层是不够的——
> ① `Elems.check` 内部额外叠了一层 Table 背景 `box.background(Styles.grayPanel)`；
> ② 它构造按钮用的 `Styles.grayt` 样式本身带 `up = grayPanel`（`Styles.java:164`），
> 而 `Button` 每帧都会按样式重设背景，所以这层必须**换样式**才能去掉。
> 本 mod 的 `PlainCheckSetting` 复用同一个 `Elems.check`（圆圈图标、悬停高亮、点击与「全部恢复默认」
> 都与原生一致），随后 `setStyle(全空的 ButtonStyle)`——新建一份空样式实例，

> 滑块与文本框仍是游戏原生样式（滑块那块「框」是它的轨道，去掉就看不出拖到哪了）。
>
> 分节标题走 `SettingsTable.Setting` 注册（`pref()`），不是直接 `add()` 进表——
> `SettingsTable.rebuild()` 每次添加设置项都会 `clearChildren()` 重建整张表，直接加的控件会被冲掉。
> 公共实现见 `src/miniassist/SectionSetting.java` 与 `src/miniassist/PlainCheckSetting.java`。

## API 契约校验

mod 依赖的每个游戏 / Arc 成员都存在被改名、改签名的风险——这类问题编译期发现不了（依赖是
`compileOnly`），只会在游戏内首次执行时以 `NoSuchFieldError` / `NoSuchMethodError` 爆出。
`tools\VerifyApi.java` 用反射逐一断言这些成员真实存在且签名匹配，等价于 JVM 链接期检查；
内存块读写的私有字段用 `getDeclaredField` + `setAccessible` 单独校验。当前覆盖 **87** 项：

```powershell
tools\verify.cmd
```

```
========================================================
[OK 私有字段] MemoryBuild.objectMemory : Object[]
[OK 私有字段] MemoryBuild.numberMemory : double[]
[OK 私有字段] MemoryBuild.sentinel (static) : Object
...
========================================================
检查成员数: 87 | 失败: 0
结果: 全部通过，mod 与 v160 API 契约一致
```

退出码非 0 即表示存在不匹配，可以直接接进 CI。

> 两个脚本的编码有讲究：`verify.ps1` 含中文路径，必须存为 **UTF-8 with BOM**（Windows PowerShell 5.1
> 读无 BOM 的 `.ps1` 会按 ANSI 解析而报语法错误）；`verify.cmd` 则保持**纯 ASCII**（cmd.exe 不认 BOM），
> 它只负责转发参数，默认值全部放在 `.ps1` 里。`verify.ps1` 的 `-JdkHome` / `-GradleHome` 默认值写死
> 本机绝对路径，换机器时用参数覆盖。

## mod 列表与详情页里的题目、描述

`mod.json` 的 `displayName` / `description` 都写**中英双语字面量**，不用 bundle 键。这不是风格选择，
而是被游戏实现逼出来的，两条独立原因：

1. **列表那一行永远不可能走 bundle**：Arc 的 `Label.setText()` 只在**字符串第 0 个字符**是 `@`（或 `$`）时
   才查 bundle（等价于 `Core.bundle.get(text.substring(1), text.toString())`，找不到就回退成原始文本）；
   而 mod 列表渲染的是 `"[accent]" + meta.displayName`（`ModsDialog`），整串以 `[accent]` 开头。
2. **详情页的 `@key` 依赖 bundle 已注册**：mod 的 bundle 由 `Mods.buildFiles()` 注册进 `Core.bundle`，
   而它**只遍历已加载的 mod**。刚把 jar 拷进 `mods/`、尚未重载/重启的那一局，`@key` 会在详情页原样
   显示成 `@miniassist.description` —— 重启后才正常。写成字面量就没有这个时间差。

**描述（description）用 `\n` 分了行**：详情页是 `desc.add(meta.description).growX().wrap(true)`，
换行会被渲染出来（`cleanup()` 只 `stripColors`，不删换行；而 `subtitle` 会被显式
`replace("\n", "")`——这也说明 description 本来就允许多行）。所以详情页读作三行：
钻机产出 / 内存块读写 / 英文一行。

**故意不写 `subtitle`**：列表第二行来自 `meta.shortDescription()`（优先 `subtitle`，否则取短于 40 字符的
`description`，两者都不满足就是空串）。本 mod 的 `description` 很长，所以不写 `subtitle` 时第二行是空白，
列表里只显示 mod 状态那一行「**支持多人游戏**」（`hidden: true` → `getStateText()` 返回
`@mod.multiplayer.compatible`）。若哪天想让列表显示一行简介，加回 `subtitle` 即可，
但会被 `Vars.maxModSubtitleLength`（40 字符）截断。

> `miniassist.description` 这个 bundle 键已删除（改成字面量后它就是死键）。
> 其余界面文案（设置项名/描述、面板数值、提示）仍然全部走 bundle，中英双语完整。

## 已知限制

- **钻机产出**只统计 `Drill` 系（`instanceof Drill.DrillBuild`），不含 `SolidPump`、`ImpactReactor` 等。
- 矿区若被建筑压住，`dominantItems` 是钻机自身按覆盖格重算的，与游戏内逻辑一致，但不会考虑未来会被
  拆掉的建筑。
- 真·联机下 `efficiency`/`warmup` 等 Continuous 量的同步精度取决于服务端发包，无法与房主端完全一致。
- **内存块读写的反射依赖游戏私有字段**，换版本可能失效（构建期由契约校验兜底，运行期会抛异常）。
- 打开逻辑编辑器时，内存块图标会停用，但钻机产出的框选仍可触发（沿用合并前行为）。
- **实机验证由作者进行**；本仓库只记录编译、符号引用与 API 契约校验结果，不含实机截图或联机实测数据。

## 性能

- 钻机产出：统计每 6 帧刷新一次，矩形每帧跟手；面板文案在刷新时才格式化并缓存，绘制期零字符串分配。
- 内存块读写：只在鼠标悬停到内存块的格子上时做一次 `tileWorld` 查询；绘制仅两个矩形。
